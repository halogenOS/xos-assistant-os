2026-09-01 12:21  core: end the run when the core can serve no message at all

A database failure used to reach the adapter as one undifferentiated
storage error, and every one of them was treated as this message's
problem: the batch halted, the loop backed off, and the update
redelivered. That is right for a refused write and for a race with
another writer. It is wrong for a database that is damaged, is not a
database, or whose one writer is gone, where the same failure meets
every later message and the intake spins against a store that can never
answer.

The core now states three distances instead of two. A failure is
terminal for its message, transient for its message, or fatal for the
process: nothing the process is asked from here on can succeed. The
fatal answer covers exactly the two classes the store hands back for
that case, an unusable database and a departed writer.

The Telegram adapter carries the fatal answer out of both its intakes.
The per-update step reports it as a stop, the poll loop persists the
offset it reached and ends the run, and the webhook consumer refuses the
delivery it was working on and ends the run. Either way the run entry
answers that the core cannot serve, the process exits, and the update is
still on the platform for the process the supervisor starts next. The
adapter reads the core's statement and never a variant name, so this is
one more answer on the edge that already existed, not a second
mechanism. The sender's authority resolution moved into a method of its
own so the step stays one readable piece.

Two tests exercise the whole path, one per intake, by killing the
store's writer thread the way a bug would: the polling run ends with the
offset unmoved, and the webhook run ends with its delivery never
acknowledged. Both fail against the old code by never ending at all.
